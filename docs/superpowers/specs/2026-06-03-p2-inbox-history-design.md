# Toss P2 接收历史与收件箱设计

**日期：** 2026-06-03

**状态：** 已评审，待进入实现计划

## 背景

Toss 当前已经完成了 P1 的接收摘要与高风险确认，用户在接收前能够知道「这次会收到什么」，也能对可执行文件进行二次确认。

但在一次传输结束之后，产品仍然偏向一次性工具：

1. 用户很难回看最近收过什么内容。
2. 失败、取消、拒绝之类的结果没有稳定的可追溯记录。
3. 传输面板只擅长展示实时状态，不适合承载长期可回看的接收记录。

P2 的第一阶段目标，是把 Toss 从「传完即散」推进到「最近发生过什么是可见的」。

## 目标

1. 在当前传输体验之外，增加一层稳定的接收历史记录。
2. 提供一个低摩擦的收件箱入口，让用户在主传输面板内就能看见最近接收记录。
3. 提供一个可展开的独立收件箱视图，用于浏览完整历史、按状态筛选、手动清理。
4. 复用 P1 已经沉淀的 `IncomingTransferSummary`，保持「概览优先」展示一致。
5. 默认保留 180 天历史记录，并支持手动清空。

## 非目标

本轮不做以下内容：

- 最近设备列表
- 常用设备置顶
- 一键重连上次设备
- 发送侧历史时间线
- 文件本体长期持久化
- 收件箱内重新下载历史文件
- 跨设备同步、云端备份、导出历史
- 文件夹级树状浏览

## 范围

本轮仅覆盖接收侧历史与收件箱。

涉及模块：

- 接收记录的数据模型
- 接收记录本地持久化
- 传输面板中的收件箱入口区
- 可展开的独立收件箱视图
- 接收结果事件到历史记录的写入逻辑
- 自动过期清理与手动清理
- 相关自动化测试

不涉及：

- 房间建立流程
- 发送面板的大结构调整
- 文件存储后端的长期归档能力

## 核心策略

### 将实时态与历史态分开

当前 `TransferItem` 主要服务于实时传输展示，包含如下特征：

- 依赖实时进度字段
- 可能持有临时 blob URL
- 关注「此刻正在发生什么」

而 P2 收件箱关注的是：

- 某次接收最终发生了什么
- 来源是谁
- 内容概览是什么
- 风险标签与结果状态是什么

因此本轮不直接把 `TransferItem` 当作持久历史表，而是新增一套独立的接收历史结构。这样可以避免：

- 临时字段污染长期记录
- blob URL 失效后把历史结构拖垮
- 实时传输逻辑和收件箱逻辑互相牵制

### 采用「内嵌入口 + 可展开视图」

本轮采用折中方案，而不是只做一个最近列表，也不是一步到位做大型独立模块。

具体策略：

1. 在当前传输面板内新增一个收件箱入口区，显示最近 3 到 5 条接收记录。
2. 提供「查看全部」入口，展开为独立的收件箱视图。
3. 传输面板继续以实时传输为主，收件箱负责承载长期回看。

这样可以同时满足两类使用场景：

- 轻量回看：刚传完，想确认刚才收到了什么
- 深度回看：想检查最近几周的接收结果、失败记录和风险条目

## 数据设计

### 新增接收历史条目

建议新增独立的接收历史类型，例如：

- `ReceiveHistoryEntry`
- 或 `InboxEntry`

推荐字段如下：

- `id`：历史记录唯一 ID
- `offerId`：关联的接收 offer ID；如果没有可用 offer，则允许为空
- `deviceId`：来源设备 ID，可为空
- `deviceName`：来源设备名
- `timestamp`：记录时间戳
- `outcome`：`completed` / `rejected` / `cancelled` / `failed`
- `summary`：`IncomingTransferSummary`
- `primaryFileName`：主文件名，用于列表首行快速展示
- `fileType`：主文件 MIME 或推导类型，可为空
- `failureReason`：失败原因文本，仅失败时可选

其中：

- `summary` 直接复用 P1 的结构，不重新发明摘要类型。
- `primaryFileName` 用于单行摘要展示，不代替完整 `summary.sampleFiles`。
- `outcome` 是本轮收件箱的核心状态字段。

### 状态模型

本轮仅记录接收侧结果，取值固定为：

- `completed`：接收完成并成功 finalize
- `rejected`：用户在确认阶段拒绝
- `cancelled`：接收中由用户主动取消
- `failed`：接收过程中断、存储失败或 finalize 失败

不记录 `pending` 和 `transferring` 这样的实时状态到历史库中。

原因是：

- 收件箱强调最终结果，而不是实时过程。
- 这样可以保持列表简洁，避免把收件箱做成第二套实时传输面板。

### 存储层

建议新增独立的浏览器本地存储模块，例如：

- `lib/receive-history-storage.ts`

采用独立的 IndexedDB store，而不是写入 `localStorage`。

原因：

1. 历史记录天然是结构化列表，IndexedDB 更适合按时间排序、扫描和清理。
2. 未来如果要扩展收藏、分页、筛选，IndexedDB 的演进空间更好。
3. 与临时的 share payload、接收文件落盘能力相比，接收历史属于另一类数据，不应混存。

### 保留策略

本轮默认策略：

- 自动保留最近 180 天的记录
- 每次读写收件箱数据时触发过期清理
- 支持手动清空全部历史

本轮不做：

- 自定义保留天数
- 单条删除
- 收藏、置顶、归档

## 写入时机

接收历史不从实时列表倒推，而是在接收事件发生时直接写入。

### 写入 `rejected`

当用户在 `file-offer` 确认阶段明确拒绝时，立即写入一条 `rejected` 记录。

写入内容应包含：

- 来源设备
- 本次摘要
- 当前时间
- 结果状态

### 写入 `completed`

当接收文件成功完成并且接收存储 finalize 成功后，写入一条 `completed` 记录。

### 写入 `cancelled`

当用户在接收过程中主动取消时，写入一条 `cancelled` 记录。

### 写入 `failed`

以下典型场景写入 `failed`：

- 接收存储创建失败
- chunk 落盘失败
- finalize 失败
- 连接中断导致接收失败，且该接收未完成

失败原因文本可以尽量简洁，例如：

- `存储初始化失败`
- `写入文件片段失败`
- `接收完成前连接中断`

### 不写入的情况

以下情况不写入历史：

- 纯文本消息
- 屏幕共享
- 系统消息
- 发送侧文件传输

## 界面设计

### 传输面板内的收件箱入口区

位置建议：

- 放在传输面板中，靠近实时传输列表上方或下方
- 与实时区视觉上分层，但不做抢主视觉的大块卡片

展示内容：

- 最近 3 到 5 条接收记录
- 每条记录展示：
  - 来源设备名
  - 时间
  - 结果状态
  - 文件概览（文件数、总大小或主文件名）

入口交互：

- 提供「查看全部」按钮
- 当没有历史时，展示简洁空态，不写成长说明文

### 独立收件箱视图

本轮优先做成当前页面内的独立展开视图，而不是新增路由。

主要包含：

1. 顶部栏
   - 标题：收件箱
   - 状态筛选
   - 清空历史按钮
   - 返回实时传输区的入口

2. 列表区
   - 按时间倒序展示
   - 默认展示记录摘要
   - 点击后展开查看更多细节

3. 详情展开信息
   - 来源设备
   - 时间
   - 文件数与总大小
   - 风险标签
   - `sampleFiles`
   - 失败原因（如有）

### 状态筛选

本轮支持以下筛选项：

- 全部
- 已接收
- 已拒绝
- 已取消
- 失败

本轮不做：

- 多条件组合筛选
- 关键字搜索
- 按设备筛选

### 记录卡片展示原则

列表项优先展示「这次是什么结果」，其次才是内容细节。

建议首行结构：

- 左侧：主标题
  - 单文件：文件名
  - 多文件：`共 N 个文件`
- 右侧：状态标签

次行结构：

- 来源设备名
- 时间
- 总大小

风险标签：

- 如果 `summary.riskFlags` 非空，则显示简洁标签，如：
  - 可执行文件
  - 超大文件
  - 批量文件

## 交互与清理

### 手动清空

收件箱视图中提供「清空历史」操作。

要求：

- 需要二次确认
- 清空后立即刷新入口区与完整列表
- 不影响实时传输项

### 自动清理

每次读取、追加、更新历史记录前，先执行过期清理。

要求：

- 过期判断基于记录时间戳与当前时间差
- 只清理超过 180 天的记录
- 清理失败不影响主流程，只记录日志

## 错误处理

### 历史写入失败

如果写入接收历史失败：

- 不得影响真实传输结果
- 不得阻塞接收或拒绝动作
- 最多记录日志，并允许 UI 继续按主流程工作

### 历史读取失败

如果收件箱读取失败：

- 入口区回退为空态
- 收件箱视图显示「暂时无法加载历史」
- 不影响实时传输区

### 历史与实时状态不一致

本轮允许「实时区显示正常，但历史区暂时没有新记录」这种降级。

优先级上：

- 真实传输结果高于历史持久化
- 收件箱是增强能力，不应反向影响传输主流程

## 文案原则

收件箱相关文案保持克制、工具化，不做聊天产品语气。

推荐方向：

- 标题：`收件箱`
- 空态：`最近的接收记录会显示在这里`
- 失败：`接收未完成`
- 已拒绝：`已拒绝`
- 已取消：`已取消`
- 已接收：`已接收`

## 测试要求

### 存储层测试

至少覆盖：

- 写入单条历史记录
- 倒序读取
- 过期清理
- 手动清空
- 存储损坏或读取失败时的降级行为

### 接收链路测试

至少覆盖：

- 接收成功后写入 `completed`
- 拒绝 offer 后写入 `rejected`
- 取消接收后写入 `cancelled`
- 存储创建或 finalize 失败后写入 `failed`
- 历史写入失败不影响主传输流程

### UI 结构测试

至少覆盖：

- 传输面板出现收件箱入口区
- 收件箱支持状态筛选
- 收件箱列表展示来源设备、时间、摘要、状态标签
- 风险标签可在历史记录中复用展示
- 清空历史入口存在

## 对后续 P2 后半段的铺垫

本轮数据结构应主动为后续能力留钩子，但不提前实现：

- 最近设备卡片上的「最近一次收到什么」
- 一键重连前的最近交互提示
- 常用设备排序时的最近活跃时间

因此本轮的接收历史条目至少要保留：

- `deviceId`
- `deviceName`
- `timestamp`
- `summary`
- `outcome`

这样后续做「最近设备」时，不需要重新回头翻实时传输项。

## 结论

P2 第一阶段采用「独立历史结构 + 本地持久化 + 面板入口 + 展开收件箱视图」的方案。

它可以在不引入文件长期归档复杂度的前提下，让 Toss 先具备稳定的接收回看能力，并为后续的最近设备与连接复用能力打下数据基础。
