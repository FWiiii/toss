# Toss P1 风险提醒与发送摘要设计

**日期：** 2026-06-03

**状态：** 已评审，待进入实现计划

## 背景

Toss 的 P1 阶段目标是让用户从「能连上」升级到「敢接收」。

当前版本已经具备以下能力：

- 接收前确认
- 设备名展示
- 会话指纹展示
- 可信设备记忆与管理

但仍存在两个明显缺口：

1. 接收确认仍然偏单文件视角，对批量发送和大文件缺少明确提醒。
2. 高风险文件没有额外保护，用户只能按普通文件一样直接接收。

本设计用于收口 P1 剩余范围，在不明显增加日常操作摩擦的前提下，补齐「风险提醒」与「本次发送内容摘要」。

## 目标

1. 让接收方在确认前看清本次发送的大致内容。
2. 对高风险内容进行分层提醒，而不是一刀切地增加所有传输摩擦。
3. 让后续 P2 的「最近设备」「接收历史」「收件箱式接收列表」可以复用本轮沉淀的摘要数据。

## 非目标

本轮不做以下内容：

- 杀毒、信誉校验、哈希比对
- MIME 深度检测或平台级安全扫描
- 文件夹树级别的完整可视化
- 接收历史持久化
- 收件箱式接收列表
- 最近设备或一键重连

## 范围

本轮仅覆盖「接收前确认」阶段。

涉及模块：

- 接收确认弹窗
- 接收文件 offer 的上下文状态
- 接收摘要与风险判定逻辑
- 相关回归测试

不涉及：

- 发送面板布局重构
- 连接建立流程重构
- 已完成传输列表结构调整

## 核心策略

采用分层确认，而不是统一强化所有文件的接收门槛。

### 普通文件

普通文件沿用现有一次确认：

- 展示设备名
- 展示本次发送摘要
- 展示会话指纹
- 支持「信任此设备」

用户点击一次「接受」即可继续。

### 批量文件与超大文件

批量文件和超大文件只做显式提醒，不增加二次确认。

默认规则：

- 单文件大小大于等于 500 MB，记为超大文件
- 本次发送文件数大于等于 10，记为批量文件

这类内容在确认框顶部展示黄色提醒区，说明：

- 为什么被标记
- 当前文件数或大小
- 这类传输可能带来的额外成本，例如耗时更久、内容更多

### 可执行文件

可执行文件进入高风险态，并要求二次确认后才能接收。

交互要求：

- 顶部展示红色高风险提醒
- 主按钮由「接受」改为「确认后接收」
- 用户必须显式勾选「我已知晓这是一类可能包含可执行内容的文件，仍然继续接收」
- 未勾选前，确认按钮不可用

## 风险判定

### 首批判定方式

首版按文件扩展名进行风险识别。

判定目标覆盖常见桌面平台的安装包和脚本，例如：

- macOS：`.app`、`.dmg`、`.pkg`
- Windows：`.exe`、`.msi`、`.bat`、`.cmd`
- Linux / 通用脚本：`.sh`、`.run`

### 判定优先级

同一次发送可能同时命中多个风险项，展示优先级如下：

1. 可执行文件
2. 超大文件
3. 批量文件

行为优先级如下：

1. 只要命中可执行文件，必须进入二次确认
2. 命中超大文件或批量文件时，只展示提醒，不追加二次确认

### 已信任设备的特殊处理

已信任设备可以继续自动接收普通文件，但不应绕过可执行文件的高风险保护。

也就是说：

- 已信任设备 + 普通文件：可自动接收
- 已信任设备 + 超大文件：可继续自动接收，后续可在系统消息中提示
- 已信任设备 + 批量文件：可继续自动接收，后续可在系统消息中提示
- 已信任设备 + 可执行文件：不得自动接收，必须进入高风险确认

本轮至少保证最后一条成立。

## 发送内容摘要

### 展示策略

多文件场景采用「概览优先」。

确认框默认展示：

- 文件总数
- 总大小
- 命中的风险项
- 前 3 个文件名

其余文件默认折叠，不在默认视图中完整展开。

### 普通单文件场景

单文件场景保留当前低摩擦展示方式：

- 文件名
- 文件大小
- 文件类型

### 多文件场景

多文件场景不再只显示当前队首文件，而是显示本次发送整体概览。

摘要文案示例：

- `共 12 个文件，总大小 842 MB`
- `包含批量文件提醒`
- `包含超大文件提醒`

文件名列表默认只展示前 3 项，示例：

1. `假期照片 01.jpg`
2. `假期照片 02.jpg`
3. `假期照片 03.jpg`

其余内容以「其余 9 个文件已折叠」的形式提示。

## 交互设计

### 普通确认态

信息结构：

1. 标题：接收文件确认
2. 描述：某设备想发送某内容
3. 内容卡片：文件摘要
4. 会话指纹
5. 「信任此设备」选项
6. 操作按钮：拒绝 / 接受

### 风险提醒态

在普通确认态基础上增加风险提醒区：

- 黄色提醒区用于批量文件和超大文件
- 红色提醒区用于可执行文件

黄色提醒区不改变原按钮逻辑。

### 高风险二次确认态

如果命中可执行文件：

1. 顶部改为高风险标题
2. 展示文件名、设备名、命中的可执行类型
3. 展示二次确认勾选项
4. 主按钮置灰，直到勾选完成

## 数据设计

当前 `IncomingFileOffer` 只够支撑单文件确认，不足以表达本次发送的整体摘要。

本轮应新增一层接收摘要信息，建议至少包含以下字段：

- `fileCount`
- `totalSize`
- `sampleFiles`
- `riskFlags`
- `requiresSecondaryConfirmation`

其中：

- `sampleFiles` 用于展示前 3 个文件
- `riskFlags` 取值至少包含 `executable`、`large`、`batch`
- `requiresSecondaryConfirmation` 用于驱动可执行文件的确认按钮状态

实现形式可以是：

1. 扩展 `IncomingFileOffer`
2. 或新增 `IncomingTransferSummary` 并由 `IncomingFileOffer` 引用

推荐第 2 种，因为后续 P2 的接收历史与收件箱也会复用这层摘要。

## 文案原则

风险提醒应克制、准确，不使用夸张和恐吓式表达。

推荐文案：

- 批量文件提醒：`本次发送包含 10 个以上文件，请确认这是你预期接收的内容。`
- 超大文件提醒：`本次发送文件较大，接收与保存可能耗时更久。`
- 可执行文件提醒：`此文件可能会在打开后运行程序，请确认来源可信后再接收。`

## 错误处理

如果摘要信息缺失或部分字段不可用：

- 不阻塞正常接收确认流程
- 回退到现有单文件信息展示
- 不展示错误风险标签

如果风险判定失败：

- 不应导致 offer 丢失
- 默认按普通文件确认处理
- 保留后续补日志和监控的接口

## 测试要求

至少补齐以下测试：

1. 普通文件仍然一次确认可接收
2. 单文件大于等于 500 MB 时出现超大文件提醒
3. 文件数大于等于 10 时出现批量文件提醒
4. 命中可执行扩展名时必须二次确认
5. 多文件摘要默认展示总数、总大小和前 3 个文件
6. 已信任设备发送可执行文件时，不得自动接收
7. 已信任设备发送普通文件时，保留原自动接收行为

如果当前测试框架不便直接做完整 UI 交互，也至少要通过架构测试覆盖：

- 风险判定逻辑存在
- 风险提醒文案存在
- 二次确认状态存在
- 自动接收保护分支存在

## 验收标准

本轮完成后，应满足以下条件：

1. 接收方能在确认前看见本次发送的整体摘要，而不只是单个文件名。
2. 超大文件和批量文件会被明确提醒，但不额外增加接收层级。
3. 可执行文件必须经过二次确认后才能接收。
4. 已信任设备不能绕过可执行文件保护。
5. 相关行为具备稳定的自动化测试覆盖。

## 对后续 P2 的铺垫

本轮新增的摘要结构将为 P2 直接复用：

- 最近接收内容的概览展示
- 收件箱式列表中的摘要信息
- 最近设备卡片上的最近一次发送内容提示

因此本轮应优先保证摘要结构清晰、边界简单，而不是把规则做得过于复杂。
